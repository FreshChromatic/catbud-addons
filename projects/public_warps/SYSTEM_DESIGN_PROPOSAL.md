## 1. 目標與批准邊界

建立一套可以由你的模組自動收集、可信投稿自動發布、其他玩家下載，以及由你在網頁管理的公共傳點系統。保留目前 Minecraft 介面的 SchematicPreview 風格與 50×50×50 預覽，改善鏡頭操作，避免兩個伺服器的同名／同 UUID 玩家互相覆蓋。

本文需要把功能、操作、資料、權限、異常、遷移、交付與必要驗證說清楚。這次只撰寫方案：不改功能、不改憑證、不遷移資料、不開新雲端服務、不部署、不執行程式測試。

批准完整方案後才進入實作；對登入設定或主機別名仍缺少的資訊，可先完成不依賴它們的部分，但不得以猜測的 API、假月卡結果或取消登入保護作為替代。任何擴大工作範圍、放寬匿名投稿或開通付費服務，都需要另行確認。

## 3. 整體架構與免費服務選擇

採用現有公共 Worker＋D1，再增加一個管理 Worker，管理 Worker 同時承載靜態管理介面。兩者使用共用業務模組與同一 D1，分開入口與登入政策。

| 元件 | 責任 | 可接觸的權限 |
|---|---|---|
| Minecraft 模組 | 補全、傳送訊號、到達計數、擷取、下載、鏡頭與投稿佇列 | 只有該電腦持有的個別投稿憑證 |
| 公共 Worker | 公開讀取、受限投稿、格式／資格／配額檢查、排程 | D1 業務讀寫，不對玩家暴露管理能力 |
| 管理 Worker | Access 登入、管理頁、審核與授權 | 驗證過的管理者可執行固定業務操作 |
| D1 | 伺服器、傳點、預覽、投稿、版本、稽核與配額 | 僅 Worker 或你的正式管理工具可存取 |
| Cloudflare Access | 管理者登入與允許名單 | 不替代業務端 JWT 驗證 |

建議管理網址使用新的 workers.dev 子域；實際名稱部署前決定。公共下載網址保持公開，不把整個公共 Worker 加上 Access，避免模組下載被登入頁擋住。管理 Worker 的所有正式及預覽入口都要驗證登入，不留下替代域名的旁路。

### 3.1 免費能力與容量界線

截至本文日期，官方資料指出：Workers 靜態資源服務免費且不限靜態請求；Worker 程式免費額度每日 100,000 請求；D1 免費每日 500 萬行讀取、10 萬行寫入、帳號總儲存 5 GB，單一免費資料庫最多 500 MB；Zero Trust 免費方案可服務最多 50 位使用者。這裡的 50 位是管理登入使用者，不是所有下載模組的玩家。[S1–S5]

因此小型管理網頁可免費提供，但管理 API、受保護的動態路由與 D1 操作仍消耗額度，不能把免費靜態資源的說明套到所有管理請求。免費 CPU 也有限；預覽解壓與格式檢查須保留界限，不承諾無限投稿吞吐量。

不啟用付費方案；若帳號要求額外啟用步驟或付款資料，先向你說明，不自行提交。維持既有邏輯 320 MiB、實體 350 MB 警戒／400 MB 停寫的保護預算，為索引、歷史、審核與遷移留下餘量。兩個伺服器共用這些總額，不能各自當成再多一份免費配額。

免費部署可行不代表所有場景已驗收：新增網頁的登入、路由與 JWT 驗證，需要一次實際驗收；超額時停止新增資料，模組仍使用已快取名單，明確顯示服務受限，不切換付費服務。

## 4. 角色、信任與來源公開

### 4.1 權限矩陣

| 操作 | 無憑證下載者 | 一般投稿者 | 可信投稿者（你） | 管理者 |
|---|---|---|---|---|
| 下載發布名單與預覽 | 可 | 可 | 可 | 可 |
| 保存本機傳點／到達次數 | 可 | 可 | 可 | 可 |
| 上傳被授權伺服器的資料 | 不可 | 可，進待審核 | 可，按規則自動發布 | 使用投稿身分時可 |
| 直接覆蓋正式預覽／狀態 | 不可 | 不可 | 僅經受限業務規則 | 可，留操作紀錄 |
| 批准、拒絕、回退、下架 | 不可 | 不可 | 不可 | 可 |
| 發放、撤銷、改可信角色 | 不可 | 不可 | 不可 | 可 |
| 任意 SQL、改 Worker／帳號 | 不可 | 不可 | 不可 | 網頁也不提供；只由帳號管理 |

可信投稿仍必須檢查 UUID／姓名、當前伺服器、輸入與尺寸、重放、間隔、容量；不因「可信」而跳過解壓上限。可信表示你願意讓這個來源自動發布，並非加密證明該模組未被修改。

投稿憑證僅在你或被授權者的設定檔；原始密鑰不寫入 Git、公開 JAR、前端資產或日誌。D1 儲存投稿密鑰雜湊。管理頁使用 Access 身分，不要求你把管理密鑰貼到瀏覽器 localStorage。現有 CLI 管理憑證作為私人救援入口保留，與網頁登入分離。

### 4.2 能保證與不能保證的事

持有源代碼的人無法僅憑源代碼取得你的私人密鑰或管理身分；服務端固定授權規則限制其可執行的操作。這是方案的管理權限邊界，不宣稱任何系統都無漏洞。

若你把可投稿的憑證給對方，對方可用自己修改的程式提交權限範圍內的資料。月卡 API 能驗證月卡，不能證明傳點仍存在，也不能證明 50³ 方塊或傳送成功訊號真實。一般投稿因此保留人工判讀；真正全面可信的自動驗證需要伺服器端提供簽章或可查詢的傳點／快照資料。

雲端收到的 serverId 也是客戶端聲明，不能證明對方真的連到該伺服器。必須把投稿者可用的 serverId 限制在其授權範圍，而非只接受任意值。

### 4.3 憑證生命周期

管理者建立投稿者 → 選擇一般／可信與 catbud／catrealm 範圍 → 產生個別密鑰 → 只顯示／下載一次 → 設定至該玩家的電腦 → 可查看近期投稿 → 撤權或輪替。

一般投稿者預設只授予一個伺服器。可信角色變更只影響新提交；既有待審核資料不因升級角色自動全數發布。撤權停止新投稿及未完成上傳票券；已發布內容不自動刪除，是否下架由管理者另行決定。

若可信密鑰洩露：立即撤銷 → 暫停該來源自動發布 → 查最近稽核 → 針對污染內容回退／下架 → 發新密鑰。恢復權限不清除稽核紀錄。

## 5. 伺服器識別與隔離

### 5.1 伺服器登錄表

| serverId | 顯示名稱 | 已知主機 | 驗證來源 |
|---|---|---|---|
| catbud | 貓芽 | catbud.net | https://api.catbud.net/discord/player/{UUID}?detailed=true；按貓芽結果獨立判定 |
| catrealm | 貓域 | catrealm.net | https://api.catrealm.net/discord/player/{UUID}?detailed=true；按貓域結果獨立判定 |

2026-10-12 使用你提供的 UUID `257205c3-c703-4034-8af8-14ee22720ceb` 實際讀取兩個接口：兩邊均回傳相同 UUID 與姓名 `YuzuCha323`，貓域 `pass: true`，貓芽 `pass: false`。這是當次觀察，不代表未來資格不變。身份與月卡必要欄位相同，可共用解析器；額外欄位並非完全一致，例如這次貓芽包含 `addons`，貓域沒有。只解析必要欄位，容許其他欄位增減，不下載或保存與傳點無關的詳細個資。

`QualificationProvider` 由服務端 serverId 登錄表選擇固定 API 網域，路徑規則相同；不接受投稿者傳入任意 API 網址，不因貓域查核失敗改用貓芽結果。資格快取、查核鎖、下次查核時間均使用 serverId＋UUID。即使兩邊姓名一致，也不能合併 pass 結果。貓域接口來源已確認，不再列為待確認事項；正常／失敗回應處理納入原有資格驗證，不另外增加大批重複測試。

主機轉小寫、移除合法連線埠後，按明確允許名單識別。子網域是否屬於相同世界／傳點網路需確認；不能只因包含 catbud 或 catrealm 字串就接受。若兩個入口連到同一組世界，可登錄為同一 serverId 的別名；若同一品牌下有獨立傳點世界，必須用額外 namespace，而不是混入同一名單。

未知／本機伺服器：可打開本機資料，但停止公共投稿和對應下載，不猜測它屬於貓芽。切服時取消傳送嘗試、擷取與鍵盤控制，異步回應必須攜帶 sessionGeneration 和 serverId，舊回應不能落到新伺服器。

### 5.2 隔離範圍

正式傳點鍵為 `(serverId, playerUuid)`；姓名是可更新屬性，不是主鍵。同一 UUID 在貓芽與貓域可以有不同預覽、名稱、用途、資格、有效狀態、更新時間。

投稿、可用性回報、票券、冷卻、待審核、回退版本、增量同步、管理操作、公開快取都必須帶 serverId。所有傳點外鍵使用相同組合鍵；只修改 warps 主鍵而漏掉其他表是不完整的隔離。

本機常用前三與成功到達次數按「本機登入帳號＋serverId」隔離，不上傳個人排行。既有以帳號＋連線位址保存的檔案，在別名合併時採一次性合併記錄；不要每次啟動重複相加到達次數。

預覽 BLOB 可依雜湊去重共用物理儲存，但公開／候選讀取仍須檢查對應伺服器的引用與權限；不能只知道雜湊就讀到待審核內容。某個伺服器下架不影響另一個伺服器仍合法引用的 BLOB。

## 6. 傳點狀態與首次紀錄規則

不要用單一 status 同時表達所有事情。將狀態分成以下維度：

| 維度 | 建議值 | 證據來源 |
|---|---|---|
| 本機發現 | candidate／confirmed／rejected_first_attempt | 補全、兩個啟動訊號、首次失敗 |
| 月卡 | unknown／active／inactive／stale | 對應伺服器的官方資格資料 |
| 可用性 | unknown／available／unavailable | 有效啟動／實際到達／失敗訊息；附來源與時間 |
| 投稿 | local_only／queued／uploading／pending_review／published／rejected／blocked | 服務端回應 |
| 發布 | unpublished／published／administratively_unpublished | 可信自動發布或管理操作 |

### 6.1 本機工作流

1. 補全出現 A：立即保存為「未試用候選」，出現在本機界面；不宣稱 A 已設傳點。
2. 發送 `/to by A`：開啟有目標、有時限的傳送嘗試。
3. 首次收到 `commands.to.target_no_pass_or_set`：移除候選，寫入 serverId＋姓名的獨立排除標記，取消首次發現投稿；不列入傳點總數。
4. 兩個對應啟動訊號確認：標記曾有效、清除首次排除標記；即使之後移動取消，也不把它當成首次無效。
5. 實際成功到達：才增加個人次數，並開始 50³ 擷取。只有啟動訊號時不能增加次數或擷取原位置。
6. 曾有效之後失敗：保留傳點與舊預覽，顯示原因／觀察時間；按鈕與雙擊仍允許再發送指令。
7. 再次成功：更新可用性、次數與預覽；不能僅因點擊重試就先清除警告。

補全消失、玩家離線、資格 API 失敗不刪除既有有效紀錄。首次排除標記可以由真正成功的手動 `/to by A` 清除；因它不在列表上，手動指令仍是恢復途徑。管理頁也可讓管理者清除誤判標記，但不偽造到達次數。

### 6.2 雲端發布門檻

名稱發現只建立未發布候選；即使來源可信、有月卡，也不能僅憑補全就把它標成有效公共傳點。可信來源的「有效啟動」或「成功到達」回報，連同身份與月卡通過後，才可自動發布。新預覽則需要實際到達後擷取。

一般投稿者的名稱／成功證據／預覽進待審核。首次失敗前若已送出候選，回報應讓候選失效；審核頁顯示「首次失敗，不可批准」，不公開到下載名單。沒有角色能以缺少首次有效證據的候選直接繞過這個規則，管理者若手動認可，須明確記錄人工確認來源。

已發布傳點月卡失效或後續傳送失敗仍留在名單。可信來源可自動更新自己的可用性觀察；一般來源回報由管理者判定，不讓陌生投稿者一筆回報就把其他人的正式傳點改成失效。官方月卡狀態獨立更新，不用人工批准。

### 6.3 資格檢查與時間順序

正常每小時檢查；上游逾時／身份不符保留最後已知資格與原查核時間，標示過期，不推導為「沒有月卡」。貓域與貓芽各查自己的 API；任一上游不可用時，僅該伺服器資格保留最後已知結果並標示過期，不影響另一伺服器。沒有足夠資格證據時該筆自動發布暫停，顯示具體原因。

伺服器處理時間負責排序、冷卻與版本；客戶端觀察時間只作附加資料，接受合理時間偏差，不讓未來時間壓住後續正常回報。不同來源相互矛盾時，官方資格優先於投稿資格，可信來源的較新觀察優先於舊觀察，管理者判定可覆寫但必須留紀錄。

## 7. 投稿、同步與發布完整工作流

### 7.1 你的可信投稿

補全／有效傳送 → 本機耐久佇列 → 查伺服器授權與身份 → 雲端收取名稱及有效性證據 → 月卡核對 → 若只有候選則保持未發布 → 有有效證據則自動發布 → 回傳正式版本 → 模組保存確認結果。

成功到達後另啟動預覽擷取：50³ 分幀讀取 → 移除玩家、文字與私有內容 → 編碼／尺寸檢查 → 上傳預檢取得票券 → 上傳 → 服務端重驗格式／大小／票券／角色 → 同一交易更新正式預覽、保留上一版、增加伺服器 revision、寫稽核 → 回傳 published 結果。

交易中任何一步失敗均不把一半新狀態公開。不讓使用者端自由指定正式版本號、管理身份或可信角色。重試使用 submissionId／冪等鍵，同一提交不產生多份正式版本或多次到達紀錄。

### 7.2 一般投稿與管理者

取得個別投稿憑證 → 模組照相同格式上傳 → 服務端驗證 → 候選保存 → 管理頁出現一筆具體提交 → 管理者比較與判斷 → 批准時重查資格與版本 → 交易發布 → 模組取得結果。

拒絕只處理該 submissionId，不把玩家傳點整筆刪除。若已存在正式版本，保持原版本。拒絕理由回傳投稿者，保持本機預覽；相同雜湊／同一證據不自動無限重投，必須有新內容或明確再提交。

### 7.3 下載流程

辨識目前 serverId → 使用該伺服器的 revision／ETag → 下載全量或增量 → 按同一 revision 完成分頁 → 合併已發布傳點 → 需要時下載該伺服器引用的預覽 → 保留個人次數與較新的本機觀察。

名單版本變更造成分頁不一致時重取該伺服器，不重取兩個伺服器。服務故障使用快取；過期增量回應要求該伺服器全量同步。切服與離開界面取消不再需要的下載。

### 7.4 上傳間隔與排隊

- 同一 serverId＋UUID 新預覽至少間隔 30 分鐘；相同雜湊不重複上傳。
- 資格正常每小時更新；兩個伺服器共用既有每日資格預算。
- 名稱批次最多 8 人，分批處理；同一個無法解析的名稱不阻擋其他人。
- 429 尊重 Retry-After；5xx／網路失敗有限退避並保留佇列；401／403 停止該憑證上傳、顯示可處理原因。
- 超過共用尺寸只保留本機完整預覽，仍可提交有效到達／名稱資料；不一直重試超大檔。
- 本機已有名稱但未同步的新憑證設定，應掃描未提交有效資料補排隊；不能只上傳「設定後第一次看見」的名稱。
- 資料過期、被拒絕、憑證失效與資料未通過資格需區分，不統一當作網路故障。

### 7.5 Minecraft 的同步呈現

主界面保持既有風格，顯示目前伺服器與總數。總數定義為此伺服器目前可列出的本機＋共用去重集合，包含未試用候選，排除首次失敗；搜尋不改變總數，可另顯示篩選結果數。

底部正常情況可只顯示「共用名單已同步」。有未投稿資料時顯示如「本機 19 · 共用 1 · 待上傳 7」；無投稿憑證時顯示「下載模式：本機資料不會上傳」，並提供簡短設定說明。不要在 UI 暴露密鑰、SQL、錯誤堆疊。

每個傳點詳情可顯示「本機」「待審核」「已共用」「僅本機預覽」與最後資格時間。候選／未知資格不阻止試用；任何失效警告仍允許傳送確認。名單刷新維持自動最短 5 分鐘、手動最短 30 秒；不是每次開啟都無條件重新下載全部。

## 8. 審核網頁：先定義判斷，再設計介面

### 8.1 管理者究竟要判斷什麼

審核頁每筆資料需回答：哪個伺服器？哪個 UUID／目前姓名？誰提交？這是首次名稱、有效性回報、預覽更新或用途修改？有何證據？官方月卡檢查何時成功？現有正式內容是什麼？批准將覆寫哪些欄位？是否有更新版本或正在上傳？是否可回退？

只提供姓名與「批准」按鈕無法支援上述判斷。也不能讓立體預覽好看就等於證明來自正確傳點。頁面要分開標示「來源可信度」「格式通過」「資格通過」「內容由管理者判讀」。

### 8.2 頁面結構與導航

| 頁面 | 主要任務 | 必須顯示 |
|---|---|---|
| 待審核（登入預設頁） | 處理有待決定的提交 | 伺服器、類型、投稿者、時間、阻擋原因、待審核數 |
| 已發布傳點 | 搜尋與維護正式資料 | 名稱／UUID、伺服器、資格／可用性、預覽版本、最後發布來源 |
| 投稿者 | 授權、撤權、信任調整 | 權限角色、伺服器範圍、啟用狀態、最近活動；不顯示原密鑰 |
| 操作紀錄 | 判斷誰改了什麼 | 動作、操作者、目標、舊／新版本、原因、結果、時間 |
| 服務狀態 | 處理上傳失敗與免費額度 | 寫入是否開放、容量、上游問題、排隊數量；用量不足時註明缺資料 |

頁首固定有「貓芽／貓域／全部」篩選、登入者與登出。跨伺服器總覽可看兩邊，但任何寫入動作只能指向一個明確伺服器。顯示時間預設 Asia/Kuala_Lumpur，資料儲存 UTC／毫秒時間戳。

### 8.3 待審核列表與詳情

桌面採左側列表＋右側詳情，最小可用寬度約 960 px；較窄時變為列表→全頁詳情，行動裝置能批准／拒絕但不強求複雜雙預覽同屏。管理網頁不仿 Minecraft 像素字體；用清楚的繁體中文文字、低裝飾、狀態字樣＋顏色，避免只有紅綠能分辨。

列表每頁 25 筆，游標分頁；預設最舊未處理優先。可按伺服器、種類、投稿者、可否批准篩選，名稱／UUID 搜尋，顯式重新整理。第一版不做每秒輪詢，不一次下載全部 5200 筆。

詳情由上到下：

1. 目標標頭：伺服器、姓名、自訂名稱、UUID（可複製）。
2. 提交摘要：提交 ID、來源、一般／可信、提交時間、類型、目前版本。
3. 判斷狀態：身份是否匹配、資格與時間、初次失敗／有效啟動／實際到達，明確說明是來源回報還是官方資料。
4. 內容比較：目前正式／本次候選並排；欄位變更清單、方塊／實體數、尺寸、雜湊、擷取時間。首次發布左側顯示「尚未發布」。
5. 原因與操作：批准並發布、拒絕這次提交、下一筆；失效回報使用「確認不可用／保留目前狀態」，不混用刪除。

固定操作區在詳情底部。批准前顯示結果摘要，如「更新貓域／A 的預覽；原預覽保留 7 天」。拒絕可選「內容不符」「重複」「來源不可信」「資訊不足」並加短說明。審核待提交不用每次再開一層泛用確認；下架、可信權限授予、撤權或批量拒絕需要具體影響確認。

### 8.4 預覽的實際可行範圍

管理網頁第一版為資料判讀工具：解碼同一份共用快照，在瀏覽器背景執行緒處理，先畫外露方塊面，按 blockId 類別上色；可旋轉／縮放，提供剖切高度查看內部。未知材質以中性色與 blockId 列表表示。實體先以類型標記／位置點顯示，列出類型與數量，不重新製作全部 Minecraft 模型。

明確標「簡化預覽」，不聲稱與遊戲預覽完全一致。兩邊視角可以同步，便於看大致結構差異；提供改變格數與方塊種類摘要。沒有必要在第一版做 125,000 格的全量差異高亮：若計算量大，使用背景計算與可取消任務。

預覽載入中不擋列表；載入失敗／格式異常顯示原因並停用批准，不靜默顯示空白；未包含預覽的有效性回報仍可依該類型規則判讀。提供下載候選資料作更深入核對，僅登入管理者可使用。瀏覽器 renderer 不載入提交內容中的腳本、外部網址或任意材質資源。

### 8.5 操作狀態、並行與錯誤

| 情況 | 頁面行為 |
|---|---|
| 沒有待審核 | 顯示「目前沒有待審核資料」，仍可切伺服器與查看發布紀錄 |
| 請求處理中 | 只鎖這筆操作，避免重複提交；保留比較內容 |
| 另一管理者已處理 | 409 提示並刷新該筆，不自動批准新內容 |
| 候選已被更新 | 保留正在看的舊提交，提示有新版；須明確切換 |
| 資格失效／上游失敗 | 顯示實際原因，批准暫停；不能把 API 失敗解釋成沒月卡 |
| 登入逾時 | 停止寫入、要求重新登入；不自動重送先前管理動作 |
| 網路超時 | 先查 submissionId 的處理結果，再決定是否重試 |
| 容量受限 | 告知新預覽無法發布；原正式內容仍可讀 |

第一版逐筆批准；不做「全部批准」。可對同一投稿者、同一伺服器、同一理由的明確選取項目批量拒絕，但若增加工作量，可先保留逐筆拒絕並列為後續增強，不影響核心交付。

處理成功返回原篩選與滾動位置，選下一筆；若從已發布頁開詳情，關閉後保留搜尋。鍵盤 Tab 可走完操作，文字可讀、按鈕有名稱，toast 不作為唯一結果證據。

## 9. 管理登入與 API 安全設計

Access 免費登入採你的明確郵箱允許名單，可使用一次性郵件登入或既有身分提供者；登入者不自動等於管理者。管理 Worker 驗證 JWT 的簽章、issuer、audience、到期與允許身分；JWKS 可合理快取並支援輪替。僅檢查某個 header 存在不能授權。[S6–S7]

管理 API 同源，寫入僅 POST／PATCH，檢查 Origin 與防 CSRF token，不開放 wildcard credential CORS；拒絕跨站與缺少必要標頭的寫入。管理回應 Cache-Control: no-store，CSP 限制腳本與連線來源，不渲染投稿內容為 HTML。日誌不記 Authorization、Access JWT、cookies 或原憑證。

所有管理動作使用 serverId＋UUID／submissionId，加 expectedRevision；業務端重新核對授權和目前狀態。操作交易記錄 requestId、操作者、來源角色、舊新版本與理由，但不儲存原密鑰。

保留 CLI 入口用于 Access 故障救援，但改為 serverId 必填（舊 CLI 可兼容 catbud 的明確預設）；不存在自動把公開投稿憑證提升成管理者的流程。管理 Worker 與公共 Worker共用領域服務，不由瀏覽器攜帶 CLI ADMIN_CREDENTIAL 轉發管理。

## 10. 資料結構與 API 合約

### 10.1 主要資料

| 表／資料物件 | 識別與重要欄位 | 設計要點 |
|---|---|---|
| servers | id、displayName、hostAliases、qualificationPolicy、enabled | 由管理設定，不接受匿名創建 |
| contributors | id、tokenHash、role、enabled、createdAt | role 為 contributor／trusted；管理者身分另行驗證 |
| contributor_servers | contributorId＋serverId | 每個來源可投稿範圍 |
| warps | serverId＋uuid；name、passState、availability、published、revision、previewHash | 正式資料與初次有效證據來源分開保存 |
| submissions | submissionId；serverId＋uuid、actor、kind、payloadHash、baseRevision、state、expiresAt | 不再一個 UUID 只有一筆且可被不同人覆蓋 |
| upload_tickets | ticketId；serverId＋uuid、actor、digest、size、expiresAt、consumed | 票券與原伺服器／來源綁定 |
| previews | digest、bytes、size、formatVersion | 可物理去重；下載另查合法引用 |
| availability_reports | reportId；serverId＋uuid、actor、reason、observedAt、receivedAt | 保留來源，不把所有回報當同等可信 |
| changes／server_revisions | serverId＋revision、uuid、published、updatedAt | 同步各伺服器獨立，不共享游標 |
| audit | actionId、serverId、target、actor、beforeRevision、afterRevision、reason、time | 回退與授權可追溯 |
| budgets | scope、key、used、expiresAt | 帳戶總額＋角色／伺服器個別限制 |

發布、拒絕、回退需要交易或原子條件更新。保留每個傳點當前版本＋上一版最多 7 天；待審核預設 7 天到期，稽核預設 30 天／最多 10,000 筆沿用現有限制。這些屬于保留策略，不代表下架資料立即物理刪除。

一般來源同一傳點最多一個有效候選，來源間互不覆蓋；每個傳點候選總量上限 5、全局有效候選最多 200，超額返回明確受限結果。可信發布不偷偷批准一般候選；一般候選若 baseRevision 已落後，標示衝突，管理員可先重新比較再批准。

### 10.2 公共 API 建議

| 端點 | 用途／保護 |
|---|---|
| GET /v2/servers | 公開支援伺服器與協議能力，不回密鑰 |
| GET /v2/servers/{serverId}/warps | 此伺服器全量名單、分頁、revision／ETag |
| GET /v2/servers/{serverId}/changes | 此伺服器增量更新／下架標記 |
| GET /v2/servers/{serverId}/previews/{hash} | 只下載此伺服器正式引用的預覽 |
| POST /v2/servers/{serverId}/discoveries | 個別憑證、範圍、身份檢查；候選不等於發布 |
| POST /v2/servers/{serverId}/observations | 有效啟動／到達／失敗回報，按角色分流 |
| POST /v2/servers/{serverId}/submissions/preflight | 格式、大小、間隔、容量與票券 |
| POST /v2/servers/{serverId}/uploads/{ticketId} | 單次上傳、內容重驗、自動發布或待審核 |
| GET /v2/submissions/{submissionId} | 只允許原投稿者看其提交結果 |

回應必須區分 received／pending_review／published／rejected／blocked，並含 reasonCode、retryAfter、serverId、revision（如適用）。HTTP 202 不等於已公開。兼容舊 /v1/warps 為 catbud 只讀視圖；舊 v1 寫入只可映射 catbud，不能推測 catrealm。公開快取鍵與 ETag 包含 serverId；名單約 60 秒快取，管理介面不快取。

### 10.3 管理 API 建議

管理 Worker 提供 session、按 serverId 的 submissions／warps、提交詳情、候選預覽、approve／reject／availability decision／metadata／rollback／unpublish、contributors grant／revoke／role／scope、audit、service status。這些是固定操作接口，沿用同一域服務，不接受 arbitrary SQL。

GET 列表分頁；POST 寫入帶 expectedRevision／submissionId／requestId；返回實際處理結果。管理 API 每次驗證登入，即使前端隱藏按鈕也不算授權。

## 11. Minecraft 預覽鏡頭的具體設計

### 11.1 體驗目標與布局

保留左側傳點格子、常用前三、右側預覽與底部傳送。單擊格子選取、雙擊格子傳送維持。右側不再雙擊切 inside 布林；避免同一雙擊在不同區域產生難以理解的模式切換。

畫面提示為「拖曳環視 · 滾輪前後 · 點擊後 WASD · R 重置」。外觀與內部只作為鏡頭當前位置描述，不需要兩個按鈕。沒有預覽時不接管控制，顯示到達後擷取提示。

### 11.2 統一鏡頭模型

相機只有 position、yaw、pitch、fov、orbitTarget、focus、navigationState；視野角固定約 60°，滾輪真正移動位置而不是改變 FOV。外觀／內部使用同一矩陣，方塊與實體共用，內部不固定在舊 eyeX／eyeY／eyeZ。

預設外觀以快照的眼睛位置為目標、完整 50³ 包圍範圍決定初始距離，保持場景可辨識。滾輪沿觀察方向前進／後退，逐步進入空間；不在門檻自動把相機傳送到眼睛位置。拍攝的 eye 用作預設目標與 reset，不限制自由移動。

移動不碰撞：預覽允許穿過方塊，方便查看封閉建築內部，不觸發遊戲傳送、世界更新或實體 tick。快照只有 50³，超出區域顯示「預覽範圍外」，不承諾可看整個伺服器。

### 11.3 操作表

| 輸入 | 條件 | 行為 |
|---|---|---|
| 左鍵拖曳 | 右側預覽有資料 | 外部繞目標旋轉；進入範圍後原地環視 |
| 滾輪向前／後 | 滑鼠在右側 | 向當前視線前進／後退；多次滾動可進出範圍 |
| 單擊預覽 | 未發生拖曳 | 取得鍵盤控制，顯示輕微焦點邊框 |
| W／S | 預覽有鍵盤焦點 | 沿視線前進／後退 |
| A／D | 同上 | 相機左右移動 |
| Space／Shift | 同上 | 世界軸上升／下降 |
| R | 同上 | 約 180 ms 平滑回預設外觀；降低動態時直接回位 |
| 右鍵 | 滑鼠在預覽 | 與 R 相同的重置；移除難用平移 |
| Esc | 預覽有焦點 | 第一次釋放控制；再按一次沿用關閉界面 |
| 點擊搜尋／列表／按鈕 | 任意 | 釋放預覽鍵盤控制，原操作正常執行 |

WASD 沿相機方向，Space／Shift 沿世界垂直軸；同時按鍵速度歸一化，斜向不加速。滾輪後退是沿當前視線反向移動；如果使用者已轉身，退出方向隨視線變化，不能強行把鏡頭跳回入口。R 始終是明確返回外觀的方法。

### 11.4 外部／內部切換與數值建議

包圍範圍使用完整快照體積，不能只根據非空氣方塊判斷。鏡頭進入略收縮的包圍體積時轉為內部環視，離開略擴張的體積時轉為外部，使用約 1 方塊滯回區，防邊界閃爍。改變拖曳規則時從當前 pose 推導 orbitTarget，不移動 camera position；過渡只改變控制權重，不跳 yaw／pitch。

初始建議：滑鼠約 0.25°／像素，俯仰限制 ±85°；WASD 4 方塊／秒，遠景按距目標適當提升，最高 20；滾輪近景約 0.5 方塊／格、遠景按距離成比例，單格最多 8。數值是一次使用者試玩可調參數，不能單靠單元測試證明手感。

輸入立即更新目標 pose；90–140 ms 指數平滑讓開始／停止可打斷；回位180 ms。按鍵用幀時間積分、限制離焦後一幀最大時間步，不按幀數積累距離；視窗失焦、鬆鍵、離開預覽、切服、換傳點、關閉界面立即清空按鍵，不能繼續漂移。

場景每幀只改矩陣，不因拖曳／WASD重新解碼或重建50³網格。保持現有多幀準備與快取機制，不為鏡頭改動擴展整體 renderer 優化工作。

### 11.5 搜尋與遊戲輸入衝突

搜尋框聚焦優先處理文字，WASD／R／Space 不移動鏡頭。遊戲中開界面保持玩家正常靜止，不能把預覽按鍵繼續傳給遊戲移動或聊天。滑鼠拖曳超過閾值約 3 px 不算單擊／雙擊；釋放預覽焦點不觸發傳點傳送。鍵盤不捕獲滑鼠，只有按住左鍵才環視，滑鼠可隨時離開操作按鈕。

## 12. 50³ 預覽、隱私與內容邊界

保留50×50×50尺寸與舊格式讀取；新方案不再次改變範圍、不升級格式除非新增serverId需要外層協議。成功到達並確認載入後分幀擷取；無法載入完整區域時等待有限時間、保留舊預覽，顯示本次未完成，不能用缺失區塊當空氣覆蓋正式版。

本機排除玩家自己；共用排除所有玩家與文字顯示實體，移除實體 UUID、自訂名稱、任意 NBT、書／牌／容器文字與私有屬性。保留經允許的實體外觀，最多64個共用實體，不把預覽實體加入真實世界或持續運行 AI。

共享保留壓縮64KiB、解壓1MiB限制；50³並不保證每種建築都能在該尺寸內。超限必須告訴玩家「本機預覽已保存，無法共用」，不偷偷裁小範圍、不降低到15³、不擴大免費儲存上限。格式損壞、未知版本、越界實體或不合法palette拒絕並保留舊正式版。

本機完整捕獲與分享副本分離，分享清理不能改變本機視覺。截取的是遊戲區域，不上傳實際世界坐標、聊天、個人訪問排行或玩家帳號設定；眼睛坐標為快照內部相對坐標。

## 13. 現有資料與協議遷移工作流

遷移只在批准及本地驗證後執行。先做D1匯出與設定備份，保留恢復資訊。不能把首次候選／曾有效狀態一律改成已驗證，也不把舊15³／30³預覽放大成50³。

1. 盤點現有表、觸發器、索引、revision、實際公開資料數量、未完成票券／候選與本機快取格式。
2. 在本地副本新增 servers、角色／scope 及 serverId 組合鍵；所有舊雲端記錄明確歸 catbud，catrealm 不複製舊紀錄。
3. 重建需要組合外鍵的表與變化觸發器；保留已有hash引用、時間、候選、權限和歷史，不簡單刪除重建資料。
4. 校驗每個舊表記錄可追溯、FK完整、舊讀接口仍只讀catbud；一次遷移測試後不反復重跑相同場景。
5. 發布支援v1兼容讀取／v2隔離的服務；短暫維護期暫停投稿寫入。遷移成功後啟用v2，舊寫入口只接受catbud兼容請求。
6. 發布新模組，遷移本機帳號＋伺服器快取。舊位址識別不明的快取保留，不硬歸catrealm；必要時一次性手動選擇。
7. 在遊戲關閉時恢復你的私人投稿設定，指定可信範圍；工具備份原設定。不能把owner憑證放入發給其他人的JAR。
8. 本機未同步候選補排隊，已確認有效的回報優先補上傳。舊預覽可先留本機，新到達再捕獲50³；使用者看到的19個不會無條件全部直接發布。
9. 一次生產讀寫檢查確認catbud正常，另確認catrealm隔離；先不上傳虛構公開預覽作為測試。

復原策略：正式資料遷移前備份＋舊Worker版本可回退；若新格式已寫入，先停止寫入並匯出新資料，再按明確遷移復原或restore方案處理，不能直接舊代碼覆蓋新表。恢復流程應保留遷移後新增資料，而不是預設清空。
